Interaction: Advanced Log Database Request

1. Collision Attacks  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:Attackers who can send a series of packets or messages may be able to overlap data. For example, packet 1 may be 100 bytes starting at offset 0. Packet 2 may be 100 bytes starting at offset 25. Packet 2 will overwrite 75 bytes of packet 1. Ensure you reassemble data before filtering it, and ensure you explicitly handle these sorts of cases.
Justification:Not applicable as a Security Level 1 threat.

2. Elevation Using Impersonation  [State: Not Applicable]  [Priority: Low] 

Category:Elevation Of Privilege
Description:OvSim.Service (LogViewerService) may be able to impersonate the context of LogViewer in order to gain additional privilege.
Justification:OvSim.Service is running as SYSTEM level, cannot elevate higher.

3. Replay Attacks  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:Packets or messages without sequence numbers or timestamps can be captured and replayed in a wide variety of ways. Implement or utilize an existing communication protocol that supports anti-replay techniques (investigate sequence numbers before timers) and strong integrity.
Justification:Not applicable as a Security Level 1 threat.

Interaction: Advanced Log Database Request

4. Insufficient Auditing  [State: Not Applicable]  [Priority: Low] 

Category:Repudiation
Description:Does the log capture enough data to understand what happened in the past? Do your logs capture enough data to understand an incident after the fact? Is such capture lightweight enough to be left on all the time? Do you have enough data to deal with repudiation claims? Make sure you log sufficient and appropriate data to handle a repudiation claims. You might want to talk to an audit expert as well as a privacy expert about your choice of data.
Justification:This is a query interation, not logging - for that see Write Logs to Database interaction.

5. Data Logs from an Unknown Source  [State: Not Applicable]  [Priority: Low] 

Category:Repudiation
Description:Do you accept logs from unknown or weakly authenticated users or systems? Identify and authenticate the source of the logs before accepting them.
Justification:This is a query interation, not logging - for that see Write Logs to Database interaction.

6. Lower Trusted Subject Updates Logs  [State: Not Applicable]  [Priority: Low] 

Category:Repudiation
Description:If you have trust levels, is anyone other outside of the highest trust level allowed to log? Letting everyone write to your logs can lead to repudiation problems. Only allow trusted code to log.
Justification:This is a query interation, not logging - for that see Write Logs to Database interaction.

7. Spoofing of Destination Data Store SQL Log Database  [State: Mitigation Implemented]  [Priority: High] 

Category:Spoofing
Description:SQL Log Database may be spoofed by an attacker and this may lead to data being written to the attacker's target instead of SQL Log Database. Consider using a standard authentication mechanism to identify the destination data store.
Justification:The OvSim.Service connects to the SQL database using user and password.

8. Risks from Logging  [State: Not Applicable]  [Priority: Low] 

Category:Tampering
Description:Log readers can come under attack via log files. Consider ways to canonicalize data in all logs. Implement a single reader for the logs, if possible, in order to reduce attack surface area. Be sure to understand and document log file elements which come from untrusted sources.
Justification:This is a query interation, not logging.

9. Potential SQL Injection Vulnerability for SQL Log Database  [State: Mitigation Implemented]  [Priority: High] 

Category:Tampering
Description:SQL injection is an attack in which malicious code is inserted into strings that are later passed to an instance of SQL Server for parsing and execution. Any procedure that constructs SQL statements should be reviewed for injection vulnerabilities because SQL Server will execute all syntactically valid queries that it receives. Even parameterized data can be manipulated by a skilled and determined attacker.
Justification:The query is fully generated by OvSim service, there&#39;s no known way to inject custom text into the query by the user.

10. Potential Weak Protections for Audit Data  [State: Mitigation Implemented]  [Priority: High] 

Category:Repudiation
Description:Consider what happens when the audit mechanism comes under attack, including attempts to destroy the logs, or attack log analysis programs. Ensure access to the log is through a reference monitor, which controls read and write separately. Document what filters, if any, readers can rely on, or writers should expect
Justification:The RemoveOldestLogs advanced database request is only available for Admin-level users.

11. Authorization Bypass  [State: Mitigation Implemented]  [Priority: High] 

Category:Information Disclosure
Description:Can you access SQL Log Database and bypass the permissions for the object? For example by editing the files directly with a hex editor, or reaching it via filesharing? Ensure that your program is the only one that can access the data, and that all other subjects have to use your interface.
Justification:The SQL log database is password protected.

12. Potential Excessive Resource Consumption for OvSim.Service (LogViewerService) or SQL Log Database  [State: Mitigation Implemented]  [Priority: High] 

Category:Denial Of Service
Description:Does OvSim.Service (LogViewerService) or SQL Log Database take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:The RemoveOldestLogs advanced database request is only available for Admin-level users. All the other advanced database requests are not available for the users, but only used within the internal software framework.
